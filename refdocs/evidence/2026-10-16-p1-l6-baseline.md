# L6 baseline: planted defects through the real verifier

> Generated by `uv run python eval/l6/run.py` (do not edit by hand). Kit 0.1.0. Fakes only, no model calls.
> **What this is:** a measured detection rate on defects someone thought of. **What it is not:** the rate on defects in general. The
> planted classes are listed below; the classes not tried are listed after them. Both lists are part of the result.

## Result

- Defects planted: **156**. Refused: **151** (97 percent of the planted set).
- Known misses (defects we believe the verifier cannot see, kept on the record): **5**: `kit-hookes-narrow-spike`, `page-wrong-label`, `page-false-prose`, `g-timer-60s-forge`, `g-coarse-pointer-forge`.
- Surprise misses (a planted defect nobody expected to pass): **0**: none.
- Neutral controls refused (false positives): **0 of 16**: none.

- Defects the post-processor is meant to neutralise rather than refuse (a model-written CSP, a comment hiding the head): **2 of 2** ended with exactly our policy, first, and no other. Not neutralised: none.

Detection among the defects the design claims to cover (planted defects minus the known misses): 151 of 151.

**Read the rate with this in mind:** the set was grown while the verifier was built, and several holes it found (attribute numbers, shadow
roots, late insertion, a forged readout at load, a wrong unit label, a wrong conversion factor) were closed because a mutation exposed
them. So this is a regression baseline that gets harder as it grows, not an unbiased estimate of detection on unseen defects.

## Which layer refused first

The harness reports the first failed rule, so this is "first to refuse", not "every layer that would have refused".

A defect whose own behaviour runs on a timer (`struct-self-moving-readout`) is refused by L1 (`control_mismatch`) or by L2 (`unstable_readout`) depending on which the harness sees first, and that varies from run to run (seen on Windows on 2026-10-18, where repeated runs gave both). It is refused every time; only the attribution moves, so a regenerated report can differ in these two rows without any change in what the verifier catches.

## Known misses, and why

- `kit-hookes-narrow-spike`: Verification samples defaults, grids and extremes; a bug confined to an unsampled point passes.
- `page-wrong-label`: Meaning of a label is not machine-checkable here; the textbook citation and a person are the defence.
- `page-false-prose`: Prose is not verified. Only grounding to a textbook (P2) and review can address it.
- `g-timer-60s-forge`: The harness cannot wait that long. The Kit's runtime self-check catches it in the student's browser and the host hides the Environment (tests: eval/l6/test_guardian_attacks.py).
- `g-coarse-pointer-forge`: The verification browser has a fine pointer. The runtime self-check catches it on the student's phone.

## Classes not tried

- Conditional or time-triggered behaviour the harness never reaches (a branch taken only on a touch screen, or after a minute). The
  verifier cannot see it. The Kit's runtime self-check catches a forged readout in the student's browser and the host closes the
  Environment (D-24); isolation (A-10) would not help with this class, only with network exfiltration.
- Bugs in the Kit that are wrong in the same way in its own reference and in the Python reference (they share an author).
- Defects in prose that contain no numbers (see the known misses), and defects in the choice of model for the question.
- Accessibility defects beyond the static fence (focus order, screen-reader reading order).
- Resource exhaustion (an endless loop, a huge allocation) beyond the render timeout.
- Multi-step attacks that depend on the host (the bridge) rather than the page.
- Anything the model could write that uses a browser feature none of us listed.

## How to read the numbers

A high rate here means the listed holes are closed. It does not mean generated Environments are correct. The two things that bound
trust are the textbook grounding (P2) and a person's review, not this table.
