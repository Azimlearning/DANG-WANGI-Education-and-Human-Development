> Hand-written. Raw numbers: `eval/golden/results/20261018T153907Z-live.json` (per call: purpose, model, tokens in and out, cost) and the pipeline trace in `data/traces.jsonl` (local, not committed). ## What ran

`uv run python eval/golden/run.py --live --ids g01`: "Why does a spring stretch when I hang a weight on it?" through the real pipeline with the real provider (plan and explain on Claude Sonnet 5.5, route fallback on Claude Haiku 5.5), the real Chromium verifier and the gate.

| Call | Model | Tokens in | Tokens out | Cost |
|---|---|---|---|---|
| route (the pattern head fell back to the model; topic, domain, complexity were answered locally) | claude-haiku-5-5 | 1,559 | 38 | $0.00017 |
| explain | claude-sonnet-5-5 | 847 | 233 | $0.00402 |
| plan | claude-sonnet-5-5 | 9,229 | 569 | $0.02415 |
| **Total** | | | | **$0.02835** |

The plan passed the plan checks at the first attempt (no retry, no repair), was assembled into a Compose-lane page, passed L0 to L3 in Chromium (11 grid points, 143 reference cases, `mechanics.hookes`) and was delivered through the gate as `model-checked`. No degrade rung was hit. 21 seconds in all: about 8 s of model time and 12 s of verification (the harness presses controls for 10 s).

The plan call is 85 percent of the cost, and about 5,000 of its input tokens are the stable prefix that is sent in full every time because prompt caching is off. Turning caching on could cut the plan cost substantially, but the ledger cannot price cache writes and reads yet (D-34), so it needs that work and a measured saving first.

## What this does NOT show (read this before quoting the numbers)

1. **The planner was shown the answer.** For a topic with a hand-written golden Plan, the exemplar in the planner prompt is that Plan (`exemplar_for`, same topic only). The model's Plan reproduces the golden Plan's numbers (a spring constant of 50 N/m, loads of 0 to 10 N). So this run shows the plumbing, the token counts and the cost, and says almost nothing about whether a model can plan an Environment on its own. A pass rate on the golden set with the exemplar would be inflated. `run.py --live --no-exemplar` withholds it for that measurement.
2. One question, one sample: no pass rate, no retry rate, no cost spread.
3. No citation: the planner prompt names no citation ids, and the run's `CORPUS_DIR` was the placeholder, so the label is `model-checked` ("no corpus configured"). That is expected and not a defect of the run.
4. No slot fill was used; the Compose lane here is a Plan assembled from Kit parts, with no model-written page code.

## What it settles

The live path works end to end with the real provider: the key, the model ids, the response parsing, the ledger booking (3 rows, $0.028347 equals the sum), the trace, and the verifier on a model-written Plan. Nothing was refused or mis-parsed. The next measurement that matters is the same run without the exemplar, on more than one question.

# Second run: three questions with NO exemplar (2026-10-18)

> Raw numbers: `eval/golden/results/20261018T155141Z-live.json`. Approved by the owner: at most $0.30. **Spent: $0.1507.** `uv run python eval/golden/run.py --live --no-exemplar --ids g01,g09,g17` (one question per topic).

| Question | Result | Calls | Cost | Time |
|---|---|---|---|---|
| g01 spring | no Environment: plan refused twice (PLAN-002, then PLAN-003 and PLAN-004) | 4 | $0.0505 | 15 s |
| g09 circuit | Environment made, `model-checked`: first plan refused (PLAN-002), the retry passed | 4 | $0.0484 | 24 s |
| g17 liquid pressure | no Environment: schema error (PLAN-001), then PLAN-002 | 4 | $0.0518 | 14 s |

**1 of 3 questions got an Environment.** Without the answer in front of it, the same planner that passed first time on the canary failed 5 of its 6 plan attempts. PLAN-002 ("use only science models listed in the Kit manifest") fired in 3 of the 6 attempts (a schema error and a wrong-parameters error made up the rest). This is a sample of three; it shows a large drop, not a rate.

## Why, found offline for free

The prompt never contained the model id. The Kit pack listed the component as `hookes({k, load})`; the Plan has to say `"model": "mechanics.hookes"`, an id that appeared nowhere in the prompt, and that string was in the prompt only when the answer-key exemplar was (it was in the exemplar's JSON). Counted over the whole golden set with the exemplar withheld: **the needed model id was in 0 of 24 prompts.** The pack also did not say which names are model inputs (bound to a slider) and which are fixed params, which fits the PLAN-003 and 004 errors on the retries.

## The change (a prompt change: commit prefix `prompt:`)

- `prompts._signature_line` now adds, for every science model, a line such as `in a Plan: "model": "mechanics.hookes"; "inputs" (each bound to a slider or constant in that unit): load [N]; "params" (fixed numbers you set): k [N/m]; returns [m]`.
- `api/prompts/planner.v2.md` (v1 kept) adds one rule: copy the model id exactly, use only the listed names, never invent an id.
- The trace now keeps the plan checks' own messages and the model ids the planner tried, and the results file carries the planning records of each question, so the next failure explains itself.

## Eval delta

| | Before | After |
|---|---|---|
| Prompts that contain the id of the model the golden Plan needs (24 questions, no exemplar), measured offline | 0 of 24 | 24 of 24 |
| Environments made from 3 questions, no exemplar, measured with the real provider | 1 of 3 ($0.1507; 1 of 6 plan attempts passed) | **3 of 3 ($0.0800; 3 of 3 plans passed at the first attempt)** |

The offline half showed the planner could see what it needs; the paid half shows it uses it.

# Third run: the same three questions after the fix (2026-10-18)

> Raw numbers: `eval/golden/results/20261018T163903Z-live.json`, which also carries each question's planning records. Approved by the owner: at most $0.20. **Spent: $0.0800.** Same command as the second run.

| Question | Result | Model chosen | Calls | Cost | Time |
|---|---|---|---|---|---|
| g01 spring | Environment, `model-checked`, first attempt | `mechanics.hookes` (k = 50) | 3 | $0.0257 | 21 s |
| g09 circuit | Environment, `model-checked`, first attempt | `electricity.ohm` | 3 | $0.0256 | 22 s |
| g17 liquid pressure | Environment, `model-checked`, first attempt | `fluids.pressure_depth` (density 1000, **g = 10**) | 3 | $0.0287 | 21 s |

- **3 of 3 made, no retries, $0.027 per Environment on average**, about 7 times below v3's roughly $0.19 (A-4, an unverified v3 figure). Tokens per question: about 11,000 in and 700 to 900 out; the plan call is 8,500 to 9,000 in and 430 to 575 out.
- **A sample of three, one per topic, on questions whose topics have hand-written Plans in the Kit.** It shows the id fix removed the dominant failure; it does not give a pass rate, and the breadth set (24 questions, other wording) has not been run.
- **The planner's values can disagree with the textbook.** For liquid pressure it chose g = 10 where the textbook uses 9.81 m s-2 in every worked problem (the golden Plan was corrected to 9.81 on the same day). The Plan is valid and the verifier accepts it; the label is `model-checked`, which says no textbook page was checked for it. A deterministic check of well-known constants against the textbook (a small table) would catch this class cheaply; not built.
- Still not measured: the 24-question set, the retry-repair behaviour on a second attempt after the fix, slot fills, and a pass rate on questions outside the Kit's coverage.
